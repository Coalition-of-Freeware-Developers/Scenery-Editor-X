# Localizing Scenery Editor X

Localization ("l10n") is the visible part of a larger job. Internationalization ("i18n") comes first: every user-facing string is marked and kept out of the code paths that build it, every widget keeps a stable identity when its label changes language, the fonts can draw the scripts the user reads, text input accepts what an input method sends, and numbers, dates and file formats stay correct whatever the user's locale. Only then can translators add languages without touching C++. For an immediate-mode Dear ImGui editor like Scenery Editor X (SEDX) the hard parts are specific: ImGui derives widget IDs and saved docking layouts from label text, it has no text shaping or right-to-left support, and CJK fonts are an order of magnitude larger than the Latin fonts SEDX ships today. The proven open-source answer is the one Godot's editor and Blender use: GNU gettext PO catalogs with the English text as the key, a small catalog loader owned by the project (neither links `libintl`), short marking functions or macros the extraction script knows, and a community translation platform (both use Weblate) that writes PO files back to the repository. The plan that follows from this research is in [`plan/feature-localization-1.md`](../plan/feature-localization-1.md). It adds a standard-library-only `i18n` module with compile-time hashed message literals, label helpers that keep every existing ImGui ID unchanged (possible since ImGui 1.92.6, where `"Text###id"` hashes the same as `"id"`), lazily merged per-language fallback fonts, a pseudo-locale for testing, a Python extraction and check tool, and a Hosted Weblate project. Right-to-left and complex scripts (Arabic, Hebrew, Persian, Thai, Devanagari) are deferred, because they need HarfBuzz shaping and a bidi pass in front of ImGui.

## What a complete localization setup covers

A setup that lets SEDX ship in other languages has to solve all of these, not just string lookup:

| Area | What it means for SEDX | Typical tool |
|---|---|---|
| Marking and extraction | Every user-facing literal goes through a function or macro the extractor recognizes, with context and translator notes where English is ambiguous ("Open" the file vs "Open" the state) | `xgettext`, project scripts |
| Catalogs | One template (POT) generated from the code, one file per language, merged when the code changes, with fuzzy flags for changed English | gettext PO/MO, JSON, XLIFF, Fluent FTL |
| Plurals | English has two forms; Russian, Ukrainian and Polish have three or more; Arabic has six; Japanese, Chinese and Korean have one. The catalog carries the rule | gettext `Plural-Forms`, CLDR plural rules |
| Placeholders | Translators must be able to reorder arguments ("{1} in {0}"), and a broken translation must never crash the editor | positional `std::format` fields, ICU MessageFormat |
| Widget identity | ImGui hashes the label into the widget ID, so a translated label changes the ID unless the stable part is separated | `"Label###id"`, `PushID` |
| Fonts | Latin, Greek and Cyrillic fit in one small font; Chinese, Japanese and Korean need 13-21 MB fonts, and Han characters need the right regional font | ImGui font merging, Noto CJK, system fonts |
| Text input | Chinese, Japanese and Korean users type through an input method editor (IME) that composes text before committing it | OS IME, ImGui `Platform_SetImeDataFn` |
| Layout | German and French run 20-40% longer than English; fixed-width columns and buttons truncate | auto-sizing, pseudo-localization |
| Locale data | Decimal separators, date formats and sort order differ, but X-Plane files must always use `.` | CLDR data, ICU, or a narrow own policy |
| Direction and shaping | Arabic and Hebrew run right to left, and Arabic and Indic scripts join or reorder glyphs | HarfBuzz, FriBidi or SheenBidi |
| Outside the editor | Installer pages, OS metadata (`Info.plist`, `.desktop`), the user manual, error dialogs | NSIS `LangString`, po4a, Weblate |
| Workflow and QA | Translators need a web UI, glossary, screenshots and checks; developers need CI that rejects broken catalogs | Weblate, Crowdin, Tolgee; `msgfmt --check`; pseudo-locales |

Microsoft's globalization guidance puts the testing side plainly: pseudo-localization (accented, lengthened, bracketed strings) finds untranslated, truncated and concatenated text before any translator starts, and it suggests lengthening English by about 40% as a heuristic ([Microsoft Learn, Pseudolocalization](https://learn.microsoft.com/globalization/methodology/pseudolocalization)). Windows even defines pseudo-locales for it: `qps-ploc`, mirrored `qps-plocm` and East-Asian `qps-ploca`.

## Three catalog models, and why the English-keyed one wins here

**Source text as key (GNU gettext PO).** The code contains `Tr("Export Scenery Pack…")`; the template lists that English text as `msgid`, and each language file adds `msgstr`. Context (`msgctxt`) separates identical English strings with different meanings, `#.` comments carry translator notes, `#:` comments point to source files, and the `Plural-Forms` header holds the language's plural rule as a C expression. When English changes, `msgmerge` (or the translation platform) keeps the old translation and marks it fuzzy instead of losing it. Every translation platform and desktop editor (Poedit, Lokalize, Weblate, Crowdin, Transifex, Tolgee) reads and writes PO. The cost is that fixing a typo in English invalidates translations of that string, and identical English strings need explicit context.

**Opaque keys (JSON, INI, XLIFF IDs).** The code contains `"hex.builtin.menu.file.open_file"_lang` and an English file maps the key to text. ImHex, a Dear ImGui hex editor, does exactly this: one flat JSON file per language, dotted keys, `fmt`-style `{}` and `{0:08X}` placeholders, and untranslated entries left as empty strings that fall back to `en_US` ([ImHex en_US.json](https://github.com/WerWolv/ImHex/blob/master/plugins/builtin/romfs/lang/en_US.json); [de_DE.json](https://github.com/WerWolv/ImHex/blob/master/plugins/builtin/romfs/lang/de_DE.json)). Keys survive English rewording, but the code no longer says what the user sees, every new string needs edits in two places, there is no plural support, and there is no fuzzy tracking, so a changed English meaning silently keeps a stale translation.

**Message-format languages (ICU MessageFormat 2, Mozilla Fluent).** These put selectors (plural, gender, select) inside the message, so translators can express grammar the code never anticipated. They are the most expressive model, but the C++ implementations are not ready: ICU 78's C++ MessageFormat 2.0 is still a technology preview at the CLDR 47 level, while only the Java side has reached "draft" ([ICU 78 announcement](https://blog.unicode.org/2025/10/icu-78-released.html); [ICU 78.3 notes](https://icu.unicode.org/)), and Fluent has no maintained general-purpose C++ library outside Firefox's Rust FFI (OpenMW started its own and described it as incomplete; [OpenMW MR 1245](https://gitlab.com/OpenMW/openmw/-/merge_requests/1245)).

For an editor whose strings are mostly short labels, tooltips and status messages, and whose translators are volunteers from the flight-sim community, PO with English keys gives the best tooling for the least code. The occasional message that needs grammar beyond plurals can be split into separate, complete sentences.

Two of the largest open-source C++ applications with community translations both own this code. Godot parses PO and MO with its own `TranslationLoaderPO`, compresses the editor catalogs with zstd into the binary, and only embeds languages that are at least 20% translated for the editor UI and 10% for the class reference, because the catalogs cost binary size ([`editor/SCsub`](https://github.com/godotengine/godot/blob/master/editor/SCsub); [`editor_translation.cpp`](https://github.com/godotengine/godot/blob/master/editor/translations/editor_translation.cpp)). Blender used Boost.Locale for years; today it reads catalogs with `blentranslation/intern/messages.cc`, a BSL-1.0 file whose header says "Adapted from boost::locale" (copyright lines run to 2025), keeping only the MO reading it needs ([messages.cc](https://github.com/blender/blender/blob/main/source/blender/blentranslation/intern/messages.cc)). SEDX has the same reasons and one more: the CPU-side code is kept standard-library-only so it builds in the Linux g++ test recipe, and the existing plans allow only MIT, BSD, Apache-2.0 or public-domain code in the app.

## How Godot and Blender mark strings

Godot's editor uses `TTR("text", "context")` for editor UI, `TTRN(singular, plural, n, context)` for counts, `DTR`/`DTRN` for the class reference, `TTRC("text")` as a no-op marker for C strings that are translated later, `RTR` for strings shown in exported games, and `ETR`/`ETRN` for strings that are only extracted ([`core/string/ustring.h`](https://github.com/godotengine/godot/blob/master/core/string/ustring.h)). It has around 40 editor PO files in `editor/translations/editor/`, all maintained on Weblate. Godot's documentation lists gettext's advantages over CSV for game projects for the same reasons: one file per locale suits Git, multi-line text is easier to edit, translation platforms such as Weblate read it, and plurals and context are supported ([Localization using gettext](https://docs.godotengine.org/en/stable/tutorials/i18n/localization_using_gettext.html)).

Blender splits strings by what they are, so users can choose what to translate: `IFACE_()` for interface labels, `TIP_()` for tooltips, `RPT_()` for reports, `DATA_()` for names of newly created data, `N_()` as a pure marker, and `CTX_IFACE_(context, text)` and friends when English is ambiguous. Each category has its own preference toggle (translate interface, tooltips, new data), and existing data names are never translated ([`BLT_translation.hh`](https://github.com/blender/blender/blob/main/source/blender/blentranslation/BLT_translation.hh); [developer guide](https://developer.blender.org/docs/handbook/translating/developer_guide/)). Translators work on Blender's own Weblate instance or offline in Poedit, with gettext's `msgfmt` and `msgmerge` as the command-line tools ([translator guide](https://developer.blender.org/docs/handbook/translating/translator_guide/)).

Three lessons carry over to SEDX. Marking functions or macros must be few and greppable, because extraction is a text scan. Only literal strings can be extracted, so dynamic labels need the "mark now, translate later" marker. And user data (airport names, file paths, library paths, art asset names) is never translated.

## Dear ImGui: identity, fonts, shaping and input

**Widget identity.** ImGui hashes a label into the widget ID, and windows, tab items, tree nodes, collapsing headers and tables persist state under that ID, including the docking layout in the `.ini` file. Translating `"PROPERTIES"` to `"EIGENSCHAFTEN"` would therefore lose the user's saved layout and collapse state, and two different English labels that happen to translate to the same word in one scope would collide (recent ImGui versions flag conflicting IDs). The `###` operator separates display text from identity. ImGui 1.92.6 (2026-02-17) changed the hash so the `###` characters themselves no longer contribute: `GetID("Hello###World") == GetID("World")` ([CHANGELOG](https://github.com/ocornut/imgui/blob/master/docs/CHANGELOG.txt)). SEDX's vendored ImGui 1.93.0 has that behaviour (`ImHashStr` resets the CRC and skips the three characters, `source/SceneryEditorX/renderer/ui/source/imgui/imgui.cpp:2620-2668`), and the `.ini` writer stores only the part after `###` (`ImHashSkipUncontributingPrefix`, line 2672). SEDX's panels are already named `"PROPERTIES###Properties"`, so a German title written as `"EIGENSCHAFTEN###Properties"` keeps the exact ID and `.ini` key (`[Window][Properties]`) it has today. The same works for labels that never had `###`: `"Löschen###Delete##node"` hashes exactly like today's `"Delete##node"`. Wrapping every translated label this way means no saved-layout migration at all.

**Fonts.** Since 1.92 the font atlas is built incrementally: with a backend that supports `ImGuiBackendFlags_RendererHasTextures`, glyph ranges no longer need to be declared, `AddFontXXX()` may be called at any time during the frame, `RemoveFont()` exists, and merged fonts are searched in order, so the first font that has a glyph supplies it ([FONTS.md](https://github.com/ocornut/imgui/blob/master/docs/FONTS.md); [CHANGELOG 1.92.0](https://github.com/ocornut/imgui/blob/master/docs/CHANGELOG.txt)). That makes lazy CJK support cheap: merge a CJK font into the UI fonts only when a CJK language is selected, and only the glyphs actually drawn get rasterized. Very large glyph sets can still exceed the GPU's maximum texture size, so `TexMaxWidth`/`TexMaxHeight` and `CompactCache()` matter for long CJK sessions. `ImFontConfig::FontNo` selects a face in a `.ttc` collection, which is how Windows and macOS ship their CJK fonts. FreeType (`imgui_freetype`, `IMGUI_ENABLE_FREETYPE`) improves small-size hinting, which helps dense CJK at 13-15 px. SEDX already compiles `imgui_freetype.cpp`, but the define is commented out (`imconfig.h:93`), so ImGui rasterizes with stb_truetype.

**Shaping and direction.** ImGui draws one glyph per code point, left to right. Its maintainer declined right-to-left support because bidi and shaping would raise CPU cost and maintenance ([issue #1228](https://github.com/ocornut/imgui/issues/1228)). Hebrew and Arabic need the Unicode Bidirectional Algorithm, and Arabic, Persian, Thai and Indic scripts also need glyph shaping. Blender, which owns its text drawing, uses FriBidi for reordering and HarfBuzz for shaping ([Blender devtalk](https://devtalk.blender.org/t/help-needed-with-rtl-complex-language-support/37819)). An ImGui application would have to shape runs itself and draw glyph IDs, not code points, which reaches into `ImFont` internals. That is a separate project; SEDX should support left-to-right scripts first. vcpkg has the parts if it is ever done: HarfBuzz 14.6.0 (MIT), SheenBidi 3.0.0 (Apache-2.0, a permissive alternative to FriBidi's LGPL) and FreeType 2.14.3 (FTL). SEDX's build already compiles HarfBuzz 13.0.1 and ICU 78.2 as Skia dependencies, though nothing links them yet.

**Input methods.** SEDX's window layer is SDL3 with ImGui's stock `imgui_impl_sdl3` backend. The backend replaces ImGui's default Win32 IME handler with its own, which tells SDL where the text cursor is through `SDL_SetTextInputArea` and turns text input on and off with `SDL_StartTextInput`/`SDL_StopTextInput` (`imgui_impl_sdl3.cpp:193-233`). Committed text arrives as `SDL_EVENT_TEXT_INPUT`. SDL 3's `SDL_HINT_IME_IMPLEMENTED_UI` defaults to `"none"`, which means the OS draws the composition and candidate windows natively (`SDL_hints.h` in the bundled SDL 3.4). So CJK typing should work without SEDX drawing pre-edit text itself. Two caveats need testing on each OS before a CJK language ships:
- The backend's own header warns that the IME "position [is] somehow broken in SDL3".
- The same header's advice to set `SDL_HINT_IME_SHOW_UI` dates from SDL2. That hint no longer exists in SDL3.

(For comparison, GLFW, which many ImGui apps use, still has no pre-edit API in 3.5.1; its pull request [#2130](https://github.com/glfw/glfw/pull/2130) is open.)

## Fonts SEDX ships, measured

The editor loads only the Open Sans family: Regular (with FontAwesome icons merged), Light, Medium, SemiBold and Bold, all at 15 px (`UILayer::LoadFonts`, `source/SceneryEditorX/renderer/ui/ui_layer.cpp:165-186`). The other files in `resources/fonts/` ship, but the UI doesn't use them.

A small script read the `cmap` table of each of those font files and of the Windows CJK system fonts, then checked sample letters for each language. So every European language, plus Russian, Ukrainian, Greek and Vietnamese, already renders with the Open Sans fonts the editor loads today. Because the Vulkan backend supports dynamic textures, the `GetGlyphRangesDefault()` passed at load time does not limit which glyphs appear: only the font file does. Industry, Cousine and Proggy would need a fallback if a future theme used them. Chinese, Japanese and Korean need an extra font per language, because Han unification means one code point is drawn differently in Japan, mainland China, Taiwan and Korea: a Chinese font showing Japanese UI text looks wrong to a Japanese reader. The cheapest correct source is the OS's own regional UI font (Microsoft YaHei / JhengHei, Yu Gothic, Malgun Gothic on Windows, all present on the English Windows 11 test machine, while Meiryo is an optional feature there and was not installed; PingFang, Hiragino and Apple SD Gothic Neo on macOS; Noto Sans CJK via fontconfig on most Linux desktops). Bundling Noto Sans CJK or Source Han Sans (SIL Open Font License 1.1) is the fallback when no system font is found. Expect a download of a similar order to the 13-21 MB system fonts above, per language.

## Numbers, dates and the C locale

X-Plane's text formats (`apt.dat`, `.dsf` text via DSFTool, `.obj`, `.fac`, `library.txt`) always use `.` as the decimal separator. The safest rule is that the editor never calls `setlocale(LC_ALL, ...)`, `setlocale(LC_NUMERIC, ...)` or `std::locale::global(...)`. `std::format` and `std::to_chars` are locale-independent unless the `L` option is used, but `printf`, `strtod` and `ImGui`'s own `%f` formatting follow the C locale, so a single global locale change would corrupt every writer and every DragFloat. Localized decimal commas in the property inspector would also be a usability trap for scenery authors, who copy coordinates between SEDX, X-Plane and WED. Dates are the one place where locale matters to users; a translator-supplied `std::format` chrono pattern per language (for example `{:%d.%m.%Y %H:%M}` in German) avoids depending on OS locale names, which differ per platform and are often not installed on Linux. Sort order (collation) of translated names would need ICU; plain code-point order is acceptable until users report it.

## Which languages first

X-Plane 12 on Steam lists eleven interface languages: English, French, Italian, German, Spanish (Spain), Japanese, Portuguese (Portugal), Russian, Simplified Chinese, Korean and Ukrainian ([Steam store page](https://store.steampowered.com/app/2014780/XPlane_12/)). Scenery authors work in X-Plane every day, so that set is a sensible target and a source of translators who already know X-Plane's terminology. Brazilian Portuguese, Polish, Czech, Dutch and Traditional Chinese are plausible next candidates, depending on who volunteers. Each costs nothing extra in code once the system exists. Arabic, Hebrew, Persian and Thai wait for the shaping work.

## What SEDX has today

A survey of `dev` at `1b079ccc` found no translation system, no catalogs and no i18n library. `vcpkg.json` lists six dependencies; ICU 78.2, HarfBuzz 13.0.1 and FreeType 2.14.3 are installed only as Skia dependencies that msdfgen pulls in. The only traces of localization are:
- an unread `ui.language = "english"` setting (`settings.cpp:71-76`);
- a panel-name comment saying "(can be localized)" (`panel_manager.h:48`);
- a commented-out Language combo in a dead settings panel.

The starting point is still better than in most applications this size:

- **Panel titles already separate text from identity.** The panel registry writes them as `"PROPERTIES###Properties"` (`source/Editor/core/editor_layer.cpp:91-114`), and the user's `editor.ini` stores `[Window][Properties]`. Translating the text before `###` changes nothing that is saved. The title is, however, written out three times (registry, each panel's `BeginPanel` call, an unused `m_Title`); one copy should remain.
- **SEDX's own wrappers carry most of the text.** `EditorUI::ItemTooltip` (185 calls), `PropertyLabel` (161), `IconLabel` (110), `SectionHeader` (43), `StripButton` (29) and `EmptyState` (9) account for about 540 of the roughly 870 live lines with UI literals. If those helpers accept a `consteval` message type through a template overload for string literals, every existing call translates without being edited.
- **Fonts and the atlas are ready.** The stock Vulkan backend supports dynamic textures, and Open Sans covers every LTR target script except CJK.
- **Locale is mostly left alone.** The only `setlocale` call is `LC_TIME` on Linux and macOS (`user_settings.cpp:129`, `:194`).

What needs work before translation can start:

- **English sentences are assembled in code.** Examples: `GetToolName(tool) + " Tool"`, `"Undo " + label`, `"Place " + name + " Here"`. About 19 sites use `== 1 ? "" : "s"` plurals. The validation messages in `project/scenery_pack.cpp:223-349` are built in AppCore with `std::to_string`.
- **Some display text doubles as file data.** `GetItemKindName` returns the same tokens the `.edX` writer serializes (`scenery_project.cpp:177-197`, `project_edx.cpp:77-78`), so display names need their own functions.
- **Commands are frozen at registration.** `EditorCommands` stores labels and tooltips as `std::string` when they are registered, so they would never follow a language change.
- **User guidance only appears through logs.** The status bar shows the latest log warning or error, there is no notification system, and some log lines are user instructions. Logs should stay English, which calls for a small user-message channel.
- **Fixed widths will clip longer languages.** Label columns are 90-170 px and buttons 130 px or less.
- **Native message boxes garble non-ASCII text.** The `ErrMsg` boxes widen UTF-8 byte by byte (`app_pch.h:125-135` and two copies). `/utf-8` reaches MSVC targets only through spdlog's interface options, so the test targets don't get it.
- **The C locale is load-bearing.** File writers print coordinates with `vsnprintf("%.8f")` (`xplane/xp_apt.cpp:123-136`, and the DSF, WED and facade writers), and parsers use `strtod`/`sscanf`. A single `setlocale(LC_ALL, "")` would corrupt every export.
- **Dates use mismatched formats.** On macOS, `GetSystemDateTimeFormat` returns an ICU date pattern that is then fed to `std::put_time` (`user_settings.cpp:69-176`, `:233-234`).
- **Fonts load before user preferences.** They load in the `Application` constructor, before `UserPreferences` is read, so the language must come from `settings.cfg`, which is available that early.
- **Nothing exists outside the editor window.** The NSIS installer is English-only (`MUI_LANGUAGE "English"`, no `LangString`). There is no `Info.plist` or `.desktop` file, and no CI (`.github/workflows` was deleted in `f6e3a53b`).

## Recommendation

1. Keep English as the source language and use gettext PO catalogs keyed by English text, one template `resources/locale/sedx.pot` and one `resources/locale/<language>.po` per language.
2. Write a standard-library-only `i18n` module: PO parser, `Plural-Forms` evaluator, BCP-47 language matching, OS language detection, and a catalog keyed by 64-bit FNV-1a hashes that a `consteval` message type computes at compile time, so a lookup costs one hash-table probe and only string literals can be passed.
3. Mark strings with a handful of functions (`Tr`, `TrN`, `TrF`, `TrL`, `TrNoop`, plus `Ctx` for context), not macros: a `TR` macro would collide with Skia's `SkRect::TR()`. Make `TrL` return `"<translation>###<original label>"`, so every ImGui ID, `editor.ini` key and `EditorLayout.json` entry stays exactly as it is now.
4. Give the `EditorUI` helpers literal-template overloads, so about 540 existing calls translate without edits. Store message literals and arguments, not finished strings, in commands, status messages and validation problems.
5. Merge per-language fallback fonts lazily (system regional font first, a downloadable Noto Sans CJK second) and keep Open Sans as the base text font.
6. Never change the process locale; keep `.` for numbers; let translators supply date patterns.
7. Add a runtime pseudo-locale (`qps-ploc`), `--language` and `--i18n-selftest` flags and a missing-string log, and take pseudo-locale screenshots of every panel.
8. Add `tools/i18n/sedx_i18n.py` (Python standard library, like the manual build) to extract the template, check catalogs (syntax, plural counts, placeholder parity) and lint for unwrapped literals. Run its checks, with the catalog unit tests, in a new CI workflow on all three OSes.
9. Translate on Hosted Weblate with a glossary of X-Plane terms, and convert the UI area by area in small pull requests.
10. Leave right-to-left and complex scripts for a later, separate project built on HarfBuzz and SheenBidi.
